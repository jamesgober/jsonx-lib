# jsonx-lib v0.5.0 — Typed, Incremental, Audited JSON

**The implementation release.** v0.5.0 reads JSON straight into your own
types and writes them straight to text, through `FromJson` and `ToJson`
impls you write by hand (no derive, no reflection, strings borrowed from the
input). It adds an incremental reader for input that arrives in chunks, a
checked push writer, output formats, and fuzzing, and fixes every finding of
the baseline audit: duplicate keys are now refused on every way of reading,
not only by `parse`, and what a read of a document can hold, a tree or typed
values, is capped (64 MiB by default) instead of growing with the input.

## What is jsonx-lib?

The JSON layer of the owner's portfolio, with no dependencies. Its consumers
are rpc-io (JSON-RPC for LSP, DAP, and MCP), lsp-lang, which drops its
rented `serde_json`, and LexerSketch's emitters. It owns JSON text: reading,
writing, escaping, and now your types, through explicit impls.

## What's new in 0.5.0

### Your types, read and written with no tree

```rust
use std::borrow::Cow;
use jsonx_lib::{json_struct, DecodeError, FromJson, Reader, ToJson, ValueWriter, Written};

struct Position { line: u32, character: u32 }
json_struct!(Position { line, character }); // both impls, for a plain struct

struct Location<'a> { uri: Cow<'a, str>, position: Position }

impl<'de> FromJson<'de> for Location<'de> {
    fn from_json(reader: &mut Reader<'de>) -> Result<Self, DecodeError> {
        let (mut uri, mut position) = (None, None);
        let mut object = reader.read_object()?;
        while let Some(key) = object.next_key()? {
            match &*key {
                "uri" => object.field(&mut uri)?,
                "position" => object.field(&mut position)?,
                _ => {} // skipped, still validated
            }
        }
        Ok(Location { uri: object.required(uri, "uri")?, position: object.required(position, "position")? })
    }
}

impl ToJson for Location<'_> {
    fn to_json(&self, out: ValueWriter<'_>) -> Written {
        out.object(|o| {
            o.member("uri", &self.uri);
            o.member("position", &self.position);
        })
    }
}

let loc: Location = jsonx_lib::from_str(r#"{"uri": "file:///a.rs", "position": {"line": 3, "character": 14}}"#)?;
assert!(matches!(loc.uri, Cow::Borrowed(_)));
assert_eq!(jsonx_lib::to_string(&loc), r#"{"uri":"file:///a.rs","position":{"line":3,"character":14}}"#);
# Ok::<(), DecodeError>(())
```

The traits:

```rust,ignore
pub trait FromJson<'de>: Sized {
    fn from_json(reader: &mut Reader<'de>) -> Result<Self, DecodeError>;
    fn absent() -> Option<Self> { None }
}

pub trait ToJson {
    fn to_json(&self, out: ValueWriter<'_>) -> Written;
    fn is_absent(&self) -> bool { false }
}
```

`FromJson` reads from the reader, so a `&'de str` or `Cow<'de, str>` field
borrows from the input. `ToJson` writes through a typed writer whose types
make one well-formed value per call a compile-time check. Impls are provided
for every primitive, the string types, `Option`, `Box`/`Rc`/`Arc`, `Vec`,
arrays, tuples up to eight, sets, string-keyed maps, and the crate's own
`Value`, `Number`, `Array`, and `Object`. A `DecodeError` is one pointer
wide and says what went wrong, at which byte, and where:
`expected u32, found string at byte 34 (at /position/line)`. `Nullable<T>`
tells LSP's absent field from its `null`; `RawValue` keeps a validated value
as text, taken from a reader with no second scan and written without a
second check (under the HTML-safe and ASCII-only formats, its strings are
escaped like any other).

### Input as it arrives

`StreamReader` is the `Reader` fed in chunks: any split, inside a token or a
UTF-8 character, gives the same events, errors, and offsets as reading the
whole text at once (a property test checks every chunking). A token cut by
a chunk boundary continues where it stopped, so input fed a byte at a time
costs linear time, and consumed input is dropped as more arrives. Both
readers read sequences of documents (NDJSON, concatenated JSON) on request.

### A checked push writer and output formats

`Writer` writes a document event by event to a `String`, an `io::Write`, or
a `fmt::Write`, and refuses any call that would break the grammar (a key
outside an object, an unclosed container, a second document). It does not
check keys for repeats: writing the same key twice in one object is your
code's to avoid, and the crate's default parser refuses the result.
`Format` sets the indent width, HTML-safe output (`<`, `>`, `&` escaped),
and ASCII-only output, for every writer.

### Duplicate keys refused on every path

In 0.2 only `parse` refused a repeated key; a `Reader`'s events let the last
value win, so the documented JSON-RPC envelope loop could be handed a
smuggled second `method` (audit JX-SEC-02). Under the default
`DuplicateKeys::Error`, every reading path now refuses it: events, raw
slices, the incremental reader, typed reads, and pointer lookups, with the
error in place of the object's `}`. The check costs a masked load, a multiply, and a bit test
per key in the common case, and for a message of ordinary shape its state is
kept inline in the reader, so it allocates nothing.

### A memory budget

0.2's default budgets let 8 MiB of `[0,0,...]` hold 256 MiB of tree (audit
JX-SEC-01). `Limits::max_memory` (64 MiB by default) now caps what one read
of a document holds, counted before it is allocated: the tree of a parse,
and the values of a typed decode (one count shared by everything the read
builds). The duplicate check's own state is capped by the same number. The
outermost array of a parse becomes its value in place, and the default
value budget is 1 Mi. The cap is absolute: a 2 MiB document of nested
zeros can still build the full 64 MiB, 32 times its size; a server that
runs many reads at once should lower `max_memory` to what its messages
need.

### Also

`json!` takes literals of thousands of single-token items (it hit the
recursion limit at 63; items that are longer expressions still fit a few
dozen); `Error::line_col` and `utf16_position` (an LSP position);
`Reader::find_pointer` (a JSON Pointer lookup that builds no tree);
`Reader::peek_kind`; `Numbers::WholeValues` for writers that spell integers
as `1e2` or `100.0`; `Value` and `Object` additions (`Hash`, `entry`,
`retain`, `sort_keys`, `pointer_mut`, 128-bit integers).

## Migration from 0.2

- **Write functions are generic** over `T: ToJson + ?Sized`. Ordinary calls
  compile unchanged. A use as a function pointer needs a closure; a
  turbofish `to_writer::<W>(..)` now names two parameters (or leave it
  out); and `to_string(&x.into())`, whose target type was inferred from
  `&Value`, needs it spelled (`to_string(&Value::from(x))`).
- **The `Reader` refuses duplicate keys** under the default policy. A raw
  event loop that needs every member asks for
  `Parser::new().duplicate_keys(DuplicateKeys::KeepAll).reader(text)`.
- **Smaller default budgets**: 1 Mi values (was 4 Mi) and the new 64 MiB
  `max_memory`. Raise them with `with_max_elements` / `with_max_memory`.
- **New `ErrorKind` variants** `MemoryLimitExceeded` and `InputAfterEnd`
  (the enum is `#[non_exhaustive]`).

## Benchmarks

### Against 0.2.0, on rpc-io's messages

rpc-io measured an early 0.5 build slower than 0.2 on small messages and
allocating more; that was fixed before release. A/B harness, 0.2.0 from
crates.io against this release on the same machine (Windows x86_64, Rust
1.99, fat LTO, a counting allocator), 31 paired samples alternating the two
versions so machine load hits both; ranges are the 10th to 90th percentile
over two builds (default, and with functions and blocks aligned, to rule out
code-alignment luck). Time is 0.5's over 0.2's (below 1 is faster):

| Input | `parse` (default policy) | allocations per `parse` | reader events (default policy) |
|---|---:|---:|---:|
| LSP hover params (~110 B) | 0.80-0.93 (409-472 ns) | 5 (0.2: 7) | 0.77-0.81 (114-121 ns); 0 allocations (0.2: 1) |
| The whole hover request (~175 B) | 0.82-0.97 | 8 (0.2: 10) | 0.72-0.97 |
| 1 MiB LSP document | 0.80-1.02 (median 0.90) | about equal | 0.87-1.18 (median 0.94-1.02) |
| 100 small integers | | | 0.54-0.67 |
| 100 short strings | | | 0.51-0.61 |

Writing the 1 MiB document takes 0.81-1.01 of 0.2's time compact and
0.85-1.17 pretty (medians 0.89 and 0.98); `read_raw` 0.84-1.08 (median
0.90).

0.2's reader did not check duplicate keys at all; 0.5's does, and is still
faster. Typed decoding of the hover params into a three-struct
`HoverParams` through `FromJson` takes 177-250 ns with no allocation (the
pre-release build: 401-491 ns, 4 allocations), against 82-118 ns for
serde_json 1.0.154's `#[derive(Deserialize)]` on the same struct: 2.3 to 2.6
times its time in paired runs (median about 2.5); on 100 short strings `Vec<&str>` is about 1.2 times serde_json, on
100 integers `Vec<u64>` about 2 times. The rest of the gap is the design:
every token goes through the one grammar state machine the incremental
reader shares, keys are handed to your code to match, and every key of every
object, skipped members included, is fingerprinted for the duplicate check.
