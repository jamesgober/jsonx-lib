# jsonx-lib v0.5.1 - Faster Writing, Same Bytes

**A writer speed release.** v0.5.1 formats floats with its own shortest
round-trip formatter instead of `core`'s, copies strings that need no
escaping in one piece, and lets the compiler see through the typed
writer's small steps. Every default format writes exactly the bytes 0.5.0
wrote. Two new `Format` options make float text match another writer's
byte for byte; with them, metrics-lib's JSON exporter writes the same text
as its `serde_json` exporter in about three quarters of the time.

## What is jsonx-lib?

The JSON layer of the owner's portfolio, with no dependencies. Its consumers
are rpc-io (JSON-RPC for LSP, DAP, and MCP), lsp-lang, LexerSketch's
emitters, and metrics-lib's JSON and OTLP/JSON exporters. It owns JSON
text: reading, writing, escaping, and your types, through explicit impls.

## What's new in 0.5.1

### Floats formatted in house

`ValueWriter::f64` and `f32`, `Number::from_f64`, and `Value::from(f64)`
used `core`'s `{:e}` and moved the decimal point. They now use Raffaello
Giulietti's Schubfach algorithm, written in this crate from the paper:
integer arithmetic, one table of 617 128-bit powers of ten, no `unsafe`,
no dependency. The text is the same as before, character for character.
The tests compare the two on about a million values and on every exponent
and boundary of both types, check every table entry against exact integer
arithmetic, and two on-demand tests compare every one of the 2^32 `f32`
values and a billion `f64`s (`cargo test --release --lib -- --ignored`);
all of them pass. Writing a float takes about a third of the time it did,
about 1.2 times what `serde_json` (with `zmij`) takes.

### Float text to match another writer

```rust
use jsonx_lib::{to_string_with, Format};

// serde_json's float text (1.0.147 and later).
let like_serde_json = Format::compact().exponent_plus(true).even_ties(true);
// 164696460098373.625 lies exactly halfway between ...373.62 and ...373.63.
let x = [1e16, 2.5e-7, 164_696_460_098_373.625];
assert_eq!(to_string_with(&x, like_serde_json), "[1e+16,2.5e-7,164696460098373.62]");
assert_eq!(jsonx_lib::to_string(&x), "[1e16,2.5e-7,164696460098373.63]");
```

- `Format::exponent_plus(true)` writes the `+` of a positive exponent:
  `1e+16`, as `serde_json`, JavaScript, and Python write it.
- `Format::even_ties(true)`: a float is written as the shortest decimal
  that reads back as it, and of those the closest; rarely (16 or 17
  significant digits) two are equally close. By default the higher one is
  written, as Rust's own formatting picks it; with this option, the one
  whose last digit is even, as `serde_json`, Java, JavaScript, and Python
  pick it. Both read back as the same float.

Both apply to floats written from Rust values; a `Number` keeps its own
text. Both are off by default, so nothing changes unless you ask.

### Strings and keys

A string with nothing to escape (most keys and most values) is tested in
whole words, at most two for 16 bytes, and copied in one piece; a longer
one is tested 16 bytes per step and, if it does need escaping, the escaping
scan starts where the test stopped instead of at the start. The key path of
`ObjectWriter` is always inlined, so for a literal key the test is done by
the compiler. The escaping itself is unchanged.

### Also

- Integers are written two digits at a time, without checking the digit
  buffer as UTF-8 before appending it; `usize` and `isize` go through the
  64-bit path.
- The typed writer's helpers are inlined, and its constant pieces (`:`,
  `true`, `false`, the exponent's `e` and sign) are appended with
  constant-length pushes instead of a length picked at run time.
- `to_string`, `to_string_pretty`, and `to_string_with` start with 128
  bytes instead of growing from 8 (four fewer reallocations for a small
  document; to allocate once for a large one, size a buffer and call
  `write_value_with`).

## Security

No change to any guarantee. The escaping rules are the same: the
whole-string test finds exactly the bytes the escaper escapes (tested at
every length and position, and against the byte-by-byte rule on arbitrary
bytes), and strict formats (`html_safe`, `ascii`) take the strict path as
before. Every float text is one valid JSON number that reads back as the
same float, with or without the new options (property-tested); the
formatter's table and arithmetic are checked exactly. No budget changed.
The only new memory use is the 128-byte first allocation of `to_string`.

## Benchmarks

Windows x86_64, Rust 1.99, release profile (fat LTO), on a machine that
was running other work throughout, so absolute times are high and noisy;
each comparison alternates the two versions and keeps the best run.

### metrics-lib's JSON snapshot

The case that prompted this release: metrics-lib's `json_bench`, a
159-series service registry (120 labeled counters, 10 histograms, gauges,
timers, rate meters, summaries; about 31 KB of compact JSON: 2 921
strings, 343 integers, 173 floats, 646 objects). A harness that keeps the
best of 40 timed batches, six runs alternating metrics-lib 2.1.0 on
jsonx-lib 0.5.0 with metrics-lib 2.1.1 on 0.5.1, both against
`serde_json` 1.0.154 in the same process:

| Writing a prepared snapshot | `serde_json` | jsonx-lib 0.5.0 | jsonx-lib 0.5.1 |
|---|---:|---:|---:|
| Compact | 30.7-31.4 µs | 70.3 µs (2.19-2.38 times `serde_json`) | 23.8 µs (0.75-0.77 times) |
| Indented | 54.5-55.8 µs | 79.3 µs | 30.1 µs |

metrics-lib's own Criterion benchmark, four alternating runs, best
medians: compact 39.4-40.2 µs for `serde_json`, 85.7 µs on 0.5.0, 25.6 µs on
0.5.1; indented 72.2-74.9, 102.6 and 43.4 µs.

Where 0.5.0's time went, measured by kind of token at the document's
counts: a float cost about 65 ns through `core`'s `{:e}` (about 120 ns
with metrics-lib's re-layout to `serde_json`'s text) against 14 ns in
`serde_json`; it now costs about 1.2 times `serde_json`'s. String escaping
was level with `serde_json`'s; the writer's call structure (helpers not
inlined across crates even under fat LTO, a push of run-time length for
every key's colon) cost most of the rest.

### `cargo bench --bench bench`

0.5.0's benchmarks and this release's, alternating, five runs; the best
Criterion median of each:

| Benchmark | 0.5.0 | 0.5.1 | 0.5.1 / 0.5.0 |
|---|---:|---:|---:|
| `to_string`, 1 MiB document | 1.78 ms | 1.67 ms | 0.93 |
| `to_string_pretty`, 1 MiB document | 3.42 ms | 2.47 ms | 0.72 |
| Typed: encode structs (`ToJson`) | 2.81 ms | 1.57 ms | 0.56 |
| `write_string`, 1 MiB, nothing to escape | 185 µs | 105 µs | 0.57 |
| `write_string`, 1 MiB, dense escapes | 2.69 ms | 2.87 ms | 1.07 * |
| `Number::from_f64`, 10 000 floats | 1.51 ms | 0.93 ms | 0.61 |

\* The escaping loop is the same code; a focused rerun of this benchmark
alone, six alternating runs, put the two within 3% (fastest runs 2.94 and
3.04 ms), inside the machine's noise. `Number::from_f64` allocates a
`String` for each number, which is most of what is left of its time.

