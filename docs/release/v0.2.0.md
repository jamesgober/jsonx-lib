# jsonx-lib v0.2.0 — Strict, Borrowing, Budgeted JSON

**The foundation.** v0.2.0 turns the scaffold into a working JSON library: a
strict RFC 8259 tokenizer whose errors name the exact byte, a document model
that borrows from its input and keeps numbers as their exact text, a pull
reader that can hand back any value as its raw source text, and a
deterministic writer whose escaping no string can break out of. Budgets are
checked before the memory they guard is allocated, and nothing recurses on
nesting depth.

## What is jsonx-lib?

The JSON layer of the owner's portfolio, with no dependencies. Its first
consumers are rpc-io (JSON-RPC for LSP, DAP, and MCP), lsp-lang (which drops
its rented `serde_json`, LexerSketch ISSUES M76), and LexerSketch's emitters.
It owns JSON text: reading, writing, escaping. It does not map JSON onto your
types by reflection; typed access is explicit.

## What's new in 0.2.0

### One call each way

```rust
use jsonx_lib::{json, parse, to_string};

let doc = parse(r#"{"name": "jsonx", "version": [0, 2, 0]}"#)?;
assert_eq!(doc["version"][1].as_u64(), Some(2));
assert_eq!(to_string(&json!({ "ok": true })), r#"{"ok":true}"#);
# Ok::<(), jsonx_lib::Error>(())
```

`parse`, `parse_bytes`, `to_string`, and `to_string_pretty` cover the common
case with default budgets and duplicate keys refused. `Parser` is the
configured path: a small `Copy` value with your `Limits` and `DuplicateKeys`
policy, defined once as a `const`.

### Exactly RFC 8259, with the offset of the mistake

Everything the grammar allows is accepted, and everything else is refused
with an `Error`: one of 21 `#[non_exhaustive]` kinds and the first byte at
which the input stops being the beginning of any valid JSON text, so the
offset points at the mistake rather than at the value that contains it.
Running out of input is always `UnexpectedEnd` at the input's length. Unpaired
UTF-16 surrogate escapes, which the grammar allows but which decode to no
Unicode text, are refused at the escape's backslash. A byte-order mark is not
whitespace.

### Borrowing, and numbers as text

Strings without escapes and every number are slices of the input. A string
with escapes is validated in one pass and decoded in a second into a buffer of
exactly its source length, so it is allocated once and never grown. `Number`
keeps the document's digits: a 30-digit integer or `19.990` round-trips
unchanged. `as_i64` and `as_u64` succeed only for integer text in range,
`as_f64` is correctly rounded and `None` when not finite, and
`Number::from_f64` writes the shortest text that reads back as the same
`f64`.

### The pull reader

`Reader` walks a document as `Event`s without building anything, and is the
state machine every parse goes through. `read_raw` consumes the next value
whole and returns its exact source text, validated but never decoded or
copied: the `RawValue` pattern a JSON-RPC server uses to keep `params` until a
handler asks for them. `read_value` builds just the part of a document you
want.

```rust
use jsonx_lib::{Event, Reader};

let mut r = Reader::new(r#"{"id": 4, "params": {"line": 3}}"#);
assert_eq!(r.next_event()?, Some(Event::StartObject));
let mut params = None;
while let Some(Event::Key(key)) = r.next_event()? {
    if &*key == "params" { params = r.read_raw()?; } else { let _skipped = r.read_raw()?; }
}
r.finish()?;
assert_eq!(params, Some(r#"{"line": 3}"#));
# Ok::<(), jsonx_lib::Error>(())
```

### Budgets before allocation

`Limits` bounds nesting depth (128 by default), input size (64 MiB), any one
string or key (16 MiB of source), any one number (1 KiB), and the count of
values (4 Mi). Each is checked before the memory it guards is used. A
counting-allocator test shows it: an 8 MiB string over a 1 KiB budget is
refused with under 1 KiB allocated, an over-size input with nothing
allocated.

### Duplicate keys refused by default

Readers that disagree about duplicate keys are a known way to smuggle a value
past a validator, so `DuplicateKeys::Error` is the default; `First`, `Last`,
and `KeepAll` are there when a protocol needs them. Keys are compared after
unescaping, by one-word fingerprints pairwise for objects of up to 16 members
and by sorting above that, so a 200,000-member object is checked in
`O(n log n)`.

### No recursion

Parsing, the reader, writing, `Clone`, `PartialEq`, and `into_owned` loop
over explicit stacks; `Drop` recurses at most a fixed 32 levels and flattens
anything deeper. A million levels of nesting are parsed, written, cloned,
compared, and dropped on a thread with a 256 KiB stack.

### The writer

Compact and pretty layouts, deterministic. `write_string` escapes `"`, `\`,
every control character, and U+2028/U+2029 (which break JSON embedded in
JavaScript), and copies everything else in bulk, found eight bytes at a time.
With `std`, `to_writer` streams through an 8 KiB buffer. `Display` is compact
JSON and `{:#}` pretty. `json!` builds values in code.

## Verification

- **Conformance:** 234 JSONTestSuite-style cases written as data from the
  RFC (73 accept, 127 refuse with a pinned kind and offset, 34
  implementation-defined with this crate's choice recorded), each also checked
  against an independent strict reference parser in the tests.
- **Properties** (proptest): verdict, value, and exact error offset agree with
  the reference parser on random token soup and on mutated valid documents;
  round trip, compact and pretty; escaping cannot inject structure, as a value
  or as a key; every truncation of a document is `UnexpectedEnd`; `read_raw`
  slices parse to their items; arbitrary bytes never panic through any entry
  point; every duplicate-key policy matches a naive reference.
- **Hostile input:** million-level nesting (refused cleanly by default,
  handled on a small stack without limits); every budget at n-1, n, n+1;
  200,000-member objects; long escape runs.
- A planted off-by-one in a literal's error offset was caught by the
  reference property at once, so the offset checks are live.

Gate (Windows): `fmt`; `clippy -D warnings` on default, all, and no-default
features, on stable, 1.85, and 1.99; `cargo doc -D warnings`; tests on stable
and 1.85, with and without `std`. With all features: 33 unit, 42 integration
(1 allocation, 12 API, 9 conformance, 10 hostile, 10 property), and 125
doctests (including every example in `README.md` and `docs/API.md`).

## Benchmarks

`cargo bench --bench bench`, release profile, Windows x86_64, one run on a
busy machine (run-to-run noise of 10–30% was observed), on an LSP-shaped
document of completion items:

| Benchmark | 1 MB | 100 MB |
|---|---:|---:|
| `parse` into a `Value` (duplicate keys refused) | ~122 MiB/s | ~81 MiB/s |
| `parse` with `DuplicateKeys::KeepAll` | ~150 MiB/s | ~82 MiB/s |
| `Reader`: every event, no tree | ~372 MiB/s | ~368 MiB/s |
| `Reader::read_raw`: validate the whole document | ~454 MiB/s | ~429 MiB/s |
| `to_string` | ~548 MiB/s | ~229 MiB/s |
| `to_string_pretty` | ~291 MiB/s | ~157 MiB/s |
| Deep `clone` | ~257 MiB/s | ~110 MiB/s |

Building a tree is bound by the allocator: the document needs about eight
allocations per completion item, and freeing them is part of each parse
measurement. During this release, profiling moved the default parse from
~69 MiB/s to ~122 MiB/s, by checking duplicates by fingerprint instead of by
sorting and by dropping shallow values without allocating. No comparison
against other JSON crates has been run yet; that is planned for 0.9.
